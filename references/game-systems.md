# 游戏系统课程 Profile

仅在用户明确讨论游戏架构、战斗、ECS、技能、属性、效果、回放、确定性模拟或网络同步时加载本文件。

## 1. 开课约束

在提供方案前，从环境读取能发现的引擎、语言、版本和现有框架，再让用户选择以下会改变架构的约束：

- 单机、联机客户端、权威服务器或混合模式。
- 实时、回合制、帧同步或状态同步。
- 对确定性、回放、预测回滚和热更新的要求。
- 实体规模、更新频率、性能预算和目标平台。
- 现有引擎对象模型、ECS、GAS 或自研框架是否必须沿用。

不要因为用户提到 ECS 就默认使用 ECS。至少比较面向对象组件、数据驱动模块、轻量 ECS 和引擎原生方案的真实成本。

## 2. 阶段映射

### Walking Skeleton

建立最小可运行循环或模拟入口：固定输入、推进一次状态、输出可验证结果。主项目同时建立模块边界和 smoke test。

### 核心抽象

根据需求选择而不是堆砌：

- Entity 或 Actor identity。
- Attribute snapshot 与 mutation contract。
- Command、Event、Effect 或 Ability 的边界。
- Target selection 与 execution context。
- 时间、随机数和 ID 的依赖注入边界。

用最复杂场景走查，例如“带暴击、护盾、持续伤害、死亡触发和网络确认的一次攻击”，画出调用链和状态变化。

### 基础设施

只实现后续子系统马上需要的能力：

- 可替换 Clock 或 Tick source。
- 可种子化 Random source。
- 稳定 ID 与 serialization boundary。
- 有明确所有权的 Event channel。
- 调试 trace、结构化日志和配置入口。
- 经测量确有需要时才增加 Pool。

避免全局 singleton、隐式当前时间、无法控制的随机数和无类型的万能事件总线；这些做法会破坏测试、回放和网络一致性。

### 子系统

按实际课程范围和依赖排序，可包含：

- 属性与派生属性。
- 伤害、治疗、护盾和死亡。
- Buff、Debuff、Effect stacking 与 duration。
- Ability cost、cooldown、targeting 与 execution。
- AI 决策或行为驱动。
- 动画、表现和音效事件桥接。
- 保存、回放或网络同步适配层。

每个子系统先独立 Demo，再在同一节接入主项目；不要先做一套互不连接的 Demo，最后一次性拼装。

## 3. 商业项目检查点

根据已选范围解释并验证：

- **Determinism**：同输入是否产生同结果，浮点、顺序和随机数如何处理。
- **Authority**：谁能修改状态，客户端请求与服务端裁决在哪里分界。
- **Replay**：记录 command、event 还是 snapshot，版本变化如何识别。
- **Serialization**：稳定 ID、schema 版本和兼容边界。
- **Debugging**：能否回答一次数值为什么变化、由谁触发、经过哪些 modifier。
- **Performance**：先测量实体数、tick 成本、分配和热点，再决定 pooling、batching 或 ECS。
- **Extensibility**：预留接口和数据边界，但不实现当前课程未承诺的网络、回滚或热更新系统。

## 4. 常见错误

- 把所有系统接入一个全局 EventBus，导致依赖不可见。
- 在伤害公式中直接读取引擎时间或全局随机数，导致测试和回放不稳定。
- 把表现逻辑写进权威状态计算，导致客户端和服务器耦合。
- 为几十个对象提前构建复杂 ECS 或对象池。
- Demo 只覆盖普通攻击，未走查叠层、死亡连锁、免疫和同步冲突。
- 只留下“未来支持网络同步”的接口名，却没有稳定状态、时间和序列化边界。

对每个错误说明它会在哪个具体需求下失败，以及当前设计如何暴露或隔离该失败。
