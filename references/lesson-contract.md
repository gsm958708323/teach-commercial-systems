# 正式课程节交付契约

## 1. 正式课程节定义

正式课程节是计划确认后、围绕一个可验证学习目标展开的最小教学单元。需求访谈、方案选择、支线答疑和单纯进度汇报不是正式课程节，不强制生成代码。

一个正式课程节可以跨多轮对话，但不得与下一课程节混在同一回复中。

## 2. 开始前

1. 运行课程恢复命令并确认当前状态。
2. 运行上一节留下的主项目基线验证；基线已通过且代码未变时不要重复运行。
3. 明确本节学习目标、最终项目增量和可运行证据。
4. 对会改变接口、数据流或模块边界的决策，先提供 3–5 个方案并等待选择。
5. 在 `.course/plan.md` 细化当前节和下一节。

## 3. 教学顺序

严格按以下顺序推进：

```text
为什么需要本能力
  -> 替代方案和权衡
  -> 接口、数据结构、依赖图
  -> 最复杂需求调用链走查
  -> 独立 Demo 完整实现
  -> 运行 Demo
  -> 主项目完整集成
  -> 针对性测试和回归测试
  -> 逐节讲解归档
  -> checkpoint
  -> 等待用户确认
```

## 4. 独立 Demo

在 `learning-labs/<course-id>/<lesson-id>/` 创建 Demo，并满足：

- 使用与主项目一致的语言和主要运行时，除非本节明确解释差异。
- 只证明一个核心原理，保持依赖和文件数量最小。
- 包含完整入口、配置和运行命令，不依赖对话中的隐藏代码。
- 不导入主项目源码；它必须能够独立运行。
- 用可观察输出、自动化测试或交互场景证明原理，而不是只打印“success”。
- 在课程文档中写明预期输出和实际结果。

Demo 是教学实现。明确指出它省略了哪些商业项目能力，不把简化代码原样称为生产实现。

## 5. 主项目集成

在同一课程节完成主项目集成：

- 将 Demo 中证明的概念映射到主项目所属模块。
- 遵循已有项目风格、模块边界和测试方式。
- 写完整实现，不用伪代码、`TODO` 或“其余省略”。
- 只增加当前课程节需要的抽象，不为假设中的未来需求建框架。
- 移除本节改动导致的未使用 import、变量和临时文件。
- 保持已有功能可运行，运行针对性测试和必要回归测试。

若只有 Demo 通过而主项目失败，将课程节标记为 `blocked`；不要以“原理已经证明”为由推进。

## 6. 讲解文档

从 `assets/templates/lesson.md` 创建 `docs/course/<course-id>/lessons/<lesson-id>.md`，至少包含：

1. 本节目标与为什么现在做。
2. 方案对比和用户选择。
3. 接口、数据结构和依赖方向。
4. 最复杂需求的调用链与状态流。
5. 独立 Demo 的文件、命令、预期和实际结果。
6. 主项目改动与代码走查。
7. Demo 简化与商业实现差异。
8. 常见错误和调试入口。
9. 已预留但本节不实现的扩展点。
10. 验证结果、自检场景和下一节依赖。

讲解“为什么”时给出具体代价，不使用“这样更好”或“业界标准”作为完整理由。

## 7. 回复格式

回复以解释为主，完整代码保存在文件中：

- 最多展示 1–2 个关键代码片段。
- 使用文件链接指向完整实现和讲解。
- 汇报真实运行命令和关键结果，不声称未运行的验证通过。
- 使用编号标题、表格和文本流程图；不使用 emoji。
- 文件路径、类名、接口名和命令使用反引号。

结尾必须包含小结、2–3 个自检场景、下一节预告，以及以下选项：

1. 进入下一节。
2. 留在本节答疑。
3. 调整后续计划。

## 8. Definition of Done

只有全部满足时才能把课程节设为 `awaiting_confirmation`：

- 学习目标和设计理由已讲清。
- 重大决策已由用户选择并记录。
- 独立 Demo 已完整生成且实际运行成功。
- 主项目实现完整，并与 Demo 的学习目标对应。
- 主项目针对性测试通过，必要回归测试通过。
- 逐节讲解文档已生成。
- checkpoint 同时记录 `demo` 和 `project` 的通过证据。
- 本节创建的主项目代码没有影响运行的占位内容。

验证失败时记录错误、当前假设和下一种不同尝试。连续三次不同尝试仍无法解决时，提供带权衡的求助选项并保持 `blocked`。
