# 学习验收轻量门槛

本文件用于确认用户学会设计原理，而不是只看到 Codex 写完代码。验收应短、具体、贴近当前课程节。

## 1. 每节学习闭环

每个正式课程节按以下闭环讲解和检查：

```text
为什么需要这个能力
  -> 不同方案各自会牺牲什么
  -> 错误设计会在哪个需求下失败
  -> 本节代码如何体现设计原则
  -> 新需求来了应该改哪里、不该改哪里
```

## 2. 设计反推题

每节结束给 2-3 个自检场景，至少一个必须是设计反推题：

- 给一个新需求，让用户判断应该修改哪个模块或接口。
- 明确问“不应该改哪里”，训练边界感。
- 给出判断标准，而不只是标准答案。

示例：

```text
新需求：订单支付回调可能重复到达。
你应该改订单状态机、支付适配器，还是前端按钮？为什么？
判断标准：重复请求是否改变已完成状态；金额校验是否仍执行；审计记录是否可追踪。
```

## 3. 用户参与方式

优先让用户在关键设计点先选择或解释，再由 Codex 评审。若用户只想快速推进，可以给参考答案，但仍要说明判断理由。

可选方式：

- 方案选择：用户从 3-5 个方案中选，并说明关注点。
- 反例分析：指出一个业余做法会在哪个需求下崩。
- 改动定位：面对新需求，判断改模块、接口、数据结构还是测试。
- 自述复盘：用 3-5 句话解释本节设计原则。

## 4. 每节记录

课程文档必须保留：

- 本节核心设计原则。
- 一个反例及其失败原因。
- 2-3 个自检场景。
- 用户若已回答，记录 Codex 的评审摘要；若未回答，记录参考判断标准。

最终 checkpoint 的 `acceptance.learning_assessment_checked` 必须为 `true`。

## 5. 反繁杂规则

- 不做长作业或考试。
- 不为了教学完整性增加无关代码。
- 不要求用户每节都写设计文档。
- 不把“回答正确”作为推进课程的硬门槛；把它作为暴露理解盲区的工具。
